# fix(webui): #39 access log 把標準庫的控制字元跳脫補回來——同機他人注入不進使用者的終端

Closes #39

`_Handler.log_message` 覆寫掉 `BaseHTTPRequestHandler.log_message` 時,連同標準庫
那一層 `message.translate(self._control_char_table)` 一起拿掉了,於是請求行裡的
path 帶著**原始 ESC** 落到 stderr——而 stderr 自 #24 起接到使用者的互動終端。
這一趟把跳脫補回來(自建一張表,不碰標準庫的私有名、不委派 `super()`),並用
原始 socket 的回歸測試把它釘住。

**行為與格式一行不改**:access log 仍是 `<method> <path> <status>` 一行三欄
(決策 9),`log_error` 仍整個收掉。改的只是「寫出去之前先過一張 translate 表」。

### 為什麼自建表,而不是委派 `super().log_message()`

票上留言 ① 要求明確選一條路,這裡選**自建表**,兩個理由:

1. `super().log_message()` 會把 `self.address_string()` 與 `log_date_time_string()`
   前綴進**每一行**。那是「只准 method / path / 狀態碼」(決策 9)之外的兩個欄位,
   其中 client ip 還是個會被寫進工單截圖的東西。委派等於用修一個洞換破一條決策。
2. `_control_char_table` 是**私有屬性**(底線開頭):CPython 任何一個小版本都可以
   把它改名或搬掉,而那會變成一個「升級 Python 之後安全防護靜默消失」的 bug。

自建表與標準庫的那張**同語意**(同一組鍵、同樣的 `\xNN` 小寫 hex、反斜線也跳脫),
所以讀 log 的人看到的字面與標準庫一致;差別只在它是這個 repo 裡看得見的一行程式碼。
`tests/test_webui_server.py::test_the_control_char_table_covers_c0_c1_and_del` 用 AST
守著「不碰 `_control_char_table`、不委派 `super().log_message`」。

反斜線為什麼也要跳脫:不跳脫的話,path 裡寫死的五個字面字元 `\x1b` 與真 ESC 跳脫
後的結果同形,讀 log 的人分不出哪一行是真的被攻擊。標準庫也跳脫它(`0x5c` 在表裡)。

兩件事順便核對成立:① 原始 `0x1b` 一個都不剩,終端收到的是**可見字面**;
② fragment(`#AAAA`)照決策 5 不進 log,query 也一樣(`_route` 兩個都切掉)。

## 已知限制

- **防的是「寫進 stderr 的那一行」,不是終端的全部輸入**。`qvault ui` 自己印的那行
  網址、Python 的 traceback(本層不印)、以及任何**別的**程序寫進同一個終端的東西,
  都不在這張票的半徑內。
- **C1 的跳脫對 UTF-8 終端是保守的**:`0x80`–`0x9f` 在 UTF-8 下不是單 byte 控制碼
  (那是 latin-1 時代的事),但請求行是以 `iso-8859-1` 解的,所以 `\x9b`(CSI)這類
  字元確實可能以單 byte 進來;表跟著標準庫一起涵蓋它們,代價只是這個區間的字元在
  log 裡變成 hex 字面。
- **gitleaks 未在本容器內實跑**(無該執行檔),見 AC-3 那一列。
