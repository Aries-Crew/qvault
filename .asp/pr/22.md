| AC | 狀態 | 證據 |

## 與票文的落差(逐條說明)

### 1. ~~一條 #21 的**時序**守門人到期了:改用新增的 `conftest.py` 標記,既有測試檔零 diff~~(已由人類側取代:那條測試已刪除,見檔首)

`tests/test_webui_server.py` 裡有一條 #21 留下的守門人:

```python
@pytest.mark.parametrize("path", ["/api/encrypt", "/api/decrypt"])
def test_the_next_tickets_endpoints_are_not_here_yet(server, path):
    """#22 的兩個端點**還不存在**——現在就回 200 的話是有人偷跑。"""
    res = send(server, path=path, payload={"path": str(GOLDEN), "passphrase": "x"})

```

它斷言的事情正是本票要交付的東西的**反面**:端點存在之後,那個請求必然不是
`404`,所以它**必然失敗**。於是「不得修改既有測試(裁判凍結)」與「交付這兩個
端點 + 全套全綠」在這一條上直接衝突。

**處置(本版改法)**:既有測試檔**一行未改**(`git diff origin/develop --
tests/test_webui_server.py` 為空),到期的那條由**新增**的 `tests/conftest.py`
在收集階段標成 `xfail(strict=True)`。選 `xfail` 而不是刪掉它、也不是 `skip`,
有三個理由:

1. **凍結條款照字面成立**:改動全在新增檔案裡(「新增測試可以」),凍結的檔案
   零 diff。
2. **那條守門人沒有消失,而是反向了**:`strict=True` 的意思是「它必須繼續
   失敗」——哪天有人把 `/api/encrypt` / `/api/decrypt` 拿掉或改回 `404`,它就會
   **XPASS**,而 strict xfail 的 XPASS 是**失敗**。於是同一條測試現在守的是
   「端點必須存在」。**這個反向守門已實測**:把 `_ENDPOINTS` 的 `decrypt` 那列
   拿掉後,它由 `xfailed` 變成 `FAILED`。
3. **它還在報告裡、總數也不減**:`120 passed, 2 xfailed`——`skip` 會讓人以為那
   條測試不重要,`xfailed` 看得見。

要讓這個標記消失,正確的做法是由**人**把那條測試從 `tests/test_webui_server.py`
刪掉(凍結是裁判的,不是施工端的),屆時 `tests/conftest.py` 的 `_EXPIRED` 清空、
整個檔案可以一起拿掉。`_EXPIRED` 刻意只有一列、且每列要寫得出理由:它是「讓一
條既有測試不紅」的唯一入口,多一列就是多一條會被濫用的捷徑。

**`xfail` 的代價,以及怎麼處理**:`xfail` 不是 `skip`,那條測試**還是會跑**,
而它的請求 `path` 是 **repo 內的 golden 向量**——於是 `/api/encrypt` 真的會寫出
`tests/vectors/golden_v1.qvt.qvt`(施工時實測)。一個會在工作樹留下檔案的測試
會讓 gate / QA 看到髒的 tree,所以 `tests/conftest.py` 在**那一條**測試的
teardown 刪掉那個**已知**產物(`_EXPIRED_ARTIFACTS`,只列確定由它寫出的路徑;
`golden_v1.qvt` 本身不在表裡也絕不該進去)。實測:跑完整個
`tests/test_webui_server.py` 之後 `git status` 乾淨。

它的後繼者在新檔裡:`test_the_api_has_exactly_three_endpoints`(含
`/api/nope`、`/api/encrypt/x`、`/api/`、`/api/Encrypt` 四種近似路徑 → `404`),
覆蓋面比原測試大。

除此之外,`tests/test_cli.py` 與**所有**既有測試檔零 diff(含 #21 那條以 `ast`
釘住相依方向的 `test_webui_only_imports_the_allowed_core_modules`:`webui` 的
`qvault_core` import 仍 ⊆ {`vault`, `container`, `errors`},本票新增的是

### 2. 「不回顯 `path` 以外的輸入欄位值」裡的 `out_dir`

見上表該列的 ⚠️:`out_dir` 的值會出現在與 CLI 逐字相同的那一句裡,而讓它不出現
就會違反同一張 AC 的「訊息逐字等於 CLI」。實作選了後者(密碼才是決策 9 的保護
對象),並以測試把「只能出現在共用常數那一句裡」釘住。

### 3. 「header 任一 byte 被改 → 訊息與錯密碼完全相同」的適用範圍

本票的 tamper 測試挑的 header 位置是 **AEAD 蓋得到的那三個欄位**(`salt`、
`nonce_prefix`、`wrapped_dek`)。`magic` 與 `version` 那幾個 byte 是另一類
(「這根本不是一個 v1 `.qvt`」→ `QVaultFormatError` / `QVaultVersionError`):
同樣 `422`,但那句話在容器被讀進來**之前**就成立,不含任何「密碼對不對」的
資訊,故 ADR-001 保證③(錯密碼與竄改不可區分)不要求它與 `AEAD authentication
failed` 同句——#21 的 `test_inspect_on_a_tampered_golden_is_422` 已經把那一類
釘在「訊息等於 CLI」上,本檔的
`test_decrypt_of_a_non_container_is_422_with_the_cli_message` 也覆蓋同一類。
測試的 docstring 寫明了這個區分。

## 施工中發現並修掉的缺陷:畸形字元會讓回應**整個消失**

端點加上之後我拿一組惡意/畸形輸入打過三個端點(孤兒代理對、NUL、5,000 字元的
路徑、字元裝置、輸出位置被同名目錄佔住……)。其中一類**不是** 4xx、也不是
`5xx`,而是**沒有回應**:

```
surrogate path (encrypt)  -> NO-RESPONSE  RemoteDisconnected: Remote end closed connection without response
surrogate path (inspect)  -> NO-RESPONSE  RemoteDisconnected: ...
surrogate out_dir         -> NO-RESPONSE  RemoteDisconnected: ...
```

成因:`json.dumps(..., ensure_ascii=False).encode("utf-8")` 對孤兒代理對
(`chr(0xDC80)`,Windows argv 與某些輸入法產生得出來,JSON 也送得進來)會拋
`UnicodeEncodeError`,而這個 encode 就發生在**錯誤出口自己**裡面(`_error`)——
拋了就沒有人能回答,連線被丟掉,客戶端連一個狀態碼都拿不到。這會讓 ADR-002
決策 14 的不變式(「任何畸形輸入都收斂成 4xx、沒有 traceback、伺服器不倒」)
與決策 8 的「`5xx` 只在未預期例外時出現」同時破掉。

修法:把兩個回應編碼點(`_json` / `_error`)收斂成一個 `_dumps`,並以
`errors="replace"` 編碼。退化成 `?` 同時是對的方向——那個字元本來就不該被
回顯(它可能是使用者密碼的一部分,鐵律 5)。修後同一組輸入:

```
surrogate path (encrypt)  -> 404 {"error": "input file does not exist: ?"}
surrogate out_dir         -> 400 {"error": "output directory does not exist: ?"}
```

- **這不是本票新長出來的洞**:同一條路徑在 `/api/inspect`(#21)就已經在了;
  本票的兩個端點各多收一個路徑欄位(`path`、`out_dir`),把暴露面擴大,所以
  在這裡一起修掉,而不是留一張票。修的是**回應編碼**,#21 任何一條斷言的行為
  都沒有變(`tests/test_webui_server.py` 的 122 項:120 passed + 2 xfailed)。
- 回歸測試:`test_a_surrogate_in_a_path_field_is_a_clean_4xx`(4 例:三個端點的
  `path` + decrypt 的 `out_dir`;斷言 4xx、鍵恰為 `{"error"}`、那個字元與它的
  `dc80` 轉義都不出現、而且伺服器之後還答得出 `200`)與
  `test_the_response_encoder_survives_an_unencodable_character`(單元層)。
  **光是跑完就已經是斷言的一部分**:修前 `send()` 會在那裡拋
  `RemoteDisconnected`。
- 已知的殘留限制(刻意如此):若磁碟上真有一個檔名不是合法 UTF-8,成功回應的
  `out` 會帶一個 `?`(路徑本身寫對了,只有回顯是有損的)。取捨很清楚——
  另一邊是「連線被丟掉、什麼都沒有」。

另外兩則探針結果,確認是**預期行為**、不改:

- 輸出位置被同名目錄佔住 + `force` → `400 {"error": "Is a directory:
  /tmp/.../.qvault-xxxxxx.part"}`:訊息帶了 `vault` 的暫存檔名。它是
  `classify` 的 `OSError` 分支**逐字照抄 CLI** 的結果(CLI 在同一情境印同一
  句),故這是「訊息只有一本帳」的必然產物,不含密碼或明文。
- `/dev/zero` → `400 input is not a regular file:`、5,000 字元路徑 →
  `400 path is not a usable file name`:都與 CLI / #21 同一句。

## 補上的覆蓋缺口:同一條連線上的連續請求(keep-alive)

`send()` **每次開一條新連線**,故「一條 TCP 連線上連續打幾個請求」原本整個沒有
測到——而那正是 #23 的頁面會做的事(瀏覽器預設重用連線)。我先用探針確認行為
是對的(一條連線上 encrypt → inspect → decrypt → encrypt 全部 `200`、
`will_close` 皆為假),再把它釘成
`test_several_requests_on_one_keep_alive_connection`。

它成立的理由是**每個回應都帶 `Content-Length`**、而且 body 在正常流程裡被讀
乾淨;任一條漏掉,下一個請求就會被接到上一個的剩餘位元組上。這條測試有牙:
把 `_respond` 的 `Content-Length` 那一行拿掉後,它**失敗**(而且是卡到逾時才
失敗——那就是「UI 整個掛住」的真實樣貌),放回去 0.2 秒通過。

## 兩處測試穩健化(跨環境)

本票的測試會在別的機器上再跑(gate / CI / QA 三關),故把兩處對環境敏感的斷言
改穩健,但**不減牙**:

- `test_the_access_log_of_the_new_endpoints_has_only_method_path_and_status`:
  原本對整個 stderr 做 `== [三行]`,別的元件哪天在 stderr 上印一條
  `ResourceWarning` 就會紅。改成先用**格式**(`[A-Z]+ /\S* \d{3}`)濾出
  access log 的行再逐行比對——濾網是格式不是內容,故「把 token 記進 path」
  那種回歸長得**像** access log、會被逐行比對抓住,另外再加三條
  (`sentinel` / `Authorization` / `Bearer` / `Traceback` 不在輸出裡)。
- `test_two_concurrent_encrypts_both_succeed`:`threading.Barrier` 的逾時
  10 秒 → 30 秒。它只是「串行就會卡住」的偵測器,不是效能斷言;受限的 runner
  上 10 秒偏緊。

## 設計上的幾個取捨(給審查看的)

- **`classify` 回 `kind` 而不是狀態碼**(裁定):`errors.py` 因此仍然 import 零個
  模組、不知道 HTTP 存在;`kind → status` 是 `webui.py` 的一張 8 列的表,
  `test_errors_module_knows_nothing_about_http` 從 AST 把這條分層釘住。
- **`_dispatch` 的未預期例外也走 `_classified`**:於是「`5xx` 的 body 只有型別名」
  在整個模組只有**一個**實作點(端點與兜底共用 `classify` 的 `unexpected` 那一列),
  不靠呼叫端自律。
- **密碼只有一個讀取點**(`_passphrase`):回傳值只有一個去處——`vault` 的參數。
  它不進網址、不進標頭、不進任何 `_Reject` 的訊息、不進 log、不進成功回應
  (成功回應的鍵恰為 `RESULT_KEYS`,只有寫出的路徑)。
- **`409` 的前置檢查不取代 `encrypt_file` 的守門**:`force` 一路傳下去,
  `test_force_reaches_the_vault_layer` 釘住;前置檢查只為了給 `409` 一句可操作的
  訊息(前置檢查與 `os.replace` 之間有 TOCTOU 窗口,見 `.asp/pr/4.md`)。
- **還原端的檔名不由 UI 決定**:`decrypt_file` 解 chunk 0、淨化檔名(ADR-001
  決策 17/21)、回傳它**實際寫出**的路徑,端點照抄進 `{"out": …}`。在 UI 層再做
  一份淨化 = 兩份會漂,而漂掉的那一份是安全檢查。
- **三個端點共用 `_input_file`**:輸入檔的三種拒絕(不存在 `404`、目錄 `400`、
  非普通檔 `400`)因此只有一份,`/api/inspect` 的既有行為與訊息逐字不變
  (#21 的三條對帳測試仍綠)。
