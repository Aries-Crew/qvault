**語料的邊界 = 本票主管層裁定 ①,逐條落在程式碼裡**(`test_webui_fuzz.py` 的模組
docstring 寫了同一段理由):

1. 所有 JSON 的 `path` 一律在 `tmp_path` 內。AC 字面寫「`path` 指向…golden」,這裡
   用的是 golden 的**複本**(`tmp_path/golden_copy.qvt`),不是 `tests/vectors/` 裡
   那一份——裁定明令不得命中它。
   **本輪更正**:上一版這句話比實際寬了一點。複審彙整項點出 kind 6(超長字串)
   原本組的是一個**相對**路徑——雖然它必定 `ENAMETOOLONG`,所以實際上碰不到任何
   東西,但那句宣稱對它不成立。現在 kind 6 也掛在 `tmp_path` 前綴下,而且這件事
   不再只是一句宣稱:`::test_every_generated_path_stays_under_tmp_path` 掃**真的
   生出來的 body**(四條路徑 × 500 筆),凡 `path` 是字串的一律要在 `tmp_path`
   底下,打到 `/api/encrypt` 的那些還要一個存在的普通檔都不是。
2. `/api/encrypt` 的 `path` 池子**不含任何存在的普通檔**,所以 `_input_file` 一定
   在 `_passphrase` 之前就拒掉 → 一次 scrypt 都不派生、一個檔都不寫。
3. `/api/decrypt` 的 `out_dir` 池子**不含任何真目錄**(`_api_decrypt` 的順序是
   輸入檔 → `out_dir` → 密碼),同樣在 KDF 之前就拒掉。

這三條前提本身由兩條**不打伺服器**的測試守著——
`::test_the_corpus_never_offers_encrypt_an_existing_path`(池子那一側)與
`::test_every_generated_path_stays_under_tmp_path`(產出那一側):前提破掉時的
徵狀(偶發多出一個 `.qvt`、偶發變慢)是最難追的那一種,所以讓語料自己先被驗一次。

另外,語料給「對的那個值」高權重(`Host` 85%、token 70%、合格 `Content-Type`
55%、POST 50%)。理由寫在檔裡:等機率的 fuzz 會讓一萬筆的九成九卡在第一道門上,
後面五道門與三個端點一個都沒走到——綠得很好看但什麼都沒驗。量尺是
`EXPECTED_AT_LEAST`:這一輪必須**真的**回過 200 / 400 / 401 / 403 / 404 / 405 /
413 / 415 / 422 各至少一次(實測分佈 `{200: 295, 400: 587, 401: 314, 403: 2097,
404: 484, 405: 5102, 413: 63, 415: 1044, 422: 14}`)。`409` 不在下界裡——它只在
encrypt 真的寫得下去時才出現,而裁定 ① 正是把那條路堵掉的。

### 判讀 ① getpass 的夾具:在新檔**複寫**一份,不搬進 `conftest.py`

### 判讀 ③ `HEAD` 的回應沒有 body,所以那一筆驗狀態碼而不驗 `error`

AC 寫「非 2xx 的 body 皆可 `json.loads` 且含 `error`」,而語料的 method 集合含
`HEAD`。依 RFC 9110 §9.3.2,`HEAD` 的回應**不得**帶 body,`_respond` 也照辦
(`if self.command != "HEAD": self.wfile.write(body)`),而 `http.client` 對 HEAD
一律把回應長度當 0 —— 所以那些筆拿到的 `body` 必然是 `b""`,`json.loads` 必然
失敗。這不是伺服器的瑕疵,是 HTTP 的規定。

處理方式:HEAD 那一支驗「狀態碼 ∈ 封閉集合」+「`body == b""`」+「`Content-Length`
標頭仍宣告出來」;其餘方法的非 2xx 驗「`json.loads` 得開 + 是 dict + 含 `error` +
`error` 是字串 + `Content-Type` 是 `application/json; charset=utf-8`」。
AC 的允許集合沒有放寬,一萬筆**每一筆**的狀態碼都照驗。

## 產品碼改動之一:`webui.py` 的方法 catch-all(裁定 ②)

主管層裁定 ② 允許「`webui.py` 補一個 catch-all,把沒有 `do_<METHOD>` 的方法統一
回 405,不讓標準庫回 501」。實作是 `_Handler.__getattr__` 的 5 行:

```python
def __getattr__(self, name: str) -> object:
    if name.startswith("do_") and len(name) > 3:
        return self._dispatch
    raise AttributeError(name)
```

**一件要先說清楚的事實**:裁定的 blocker 敘述(「fuzz 的 method 集合含
PUT / DELETE / HEAD / OPTIONS，而 CPython 對沒有 `do_<METHOD>` 的方法回 501」)
對本票的語料**其實不成立**——`_Handler` 從 #21 起就有
`do_GET` / `do_HEAD` / `do_POST` / `do_PUT` / `do_PATCH` / `do_DELETE` / `do_OPTIONS`
七個具名賦值,而 AC 的 method 集合(GET / POST / PUT / DELETE / HEAD / OPTIONS)
是它的子集。所以**就算不改 `webui.py`,fuzz 也不會碰到 501**。

那為什麼還是改了:裁定授權的那件事本身是對的,而且改完之後「不回 501」從「我們
恰好列了七個動詞」變成**型別層面成立**。`TRACE` / `PROPFIND` / `BREW` 這些動詞
打進來時,原本會拿到標準庫的 `501` + 一份 **HTML** 錯誤頁 —— 狀態碼不在決策 14
的封閉集合裡,body 不是本層唯一的錯誤形式,還順手把「這是個
`BaseHTTPRequestHandler`」告訴了打進來的人。現在它們拿到跟 `PUT /` 一模一樣的
那一句 `405 {"error": "method not allowed"}`。

邊界守得很緊,三件事值得記下來:

1. **沒有放行任何方法。** catch-all 只決定「進不進 `_dispatch`」;受不受理仍由
   `_handle` 判(靜態路由只收 GET / HEAD,`/api/*` 只收 POST)。所以那七個具名
   賦值不是白名單,只是具名的常見動詞;上面那串保留著不刪,它們比
   `__getattr__` 好讀。
2. **只接 `do_` 開頭的名字**,其餘照常 `AttributeError`。`_drain_request_body` 的
   `getattr(self, "headers", None)` 與 `_route` 的 `getattr(self, "path", "")` 必須
   維持「真的沒有就是沒有」的語意 —— 那兩個預設值處理的正是「請求行還沒解析成功」
   的情況,一個吃掉所有名字的 `__getattr__` 會把它們變成「永遠拿得到東西」。
   `::test_the_catch_all_only_answers_do_names` 直接斷言 `do_` / `headers` /
   `path` / `_body_consumed` / `nope` 五個名字照樣拋 `AttributeError`。
3. **AC 的允許集合沒有放寬**,501 沒有被納入。`ALLOWED_STATUS` 逐字就是票文那
   十個碼。

補的測試:`::test_an_unknown_method_is_405_json_not_501_html`(5 個動詞 × 3 條
路徑 = 15 格,逐格驗 405 + `{"error": "method not allowed"}` + JSON
`Content-Type` + 三個安全標頭)、`::test_the_catch_all_only_answers_do_names`、
`::test_an_unknown_method_does_not_print_a_traceback`(順帶驗 access log 仍是
`<method> <path> <status>` 一行)。

## 產品碼改動之二:`_respond` 的殘留 body 收尾(合併前複審的擋合併項)

複審在負載下看到 fuzz 偶發連線錯誤,推定根因是產品缺陷,主管層以 raw socket
**確定性重現**(不需負載)並授權第二處產品碼改動。那個缺陷是真的,而且比
「fuzz 偶發紅」嚴重:

`GET /` 帶一個宣告了 `Content-Length` 的 body 是合法的 HTTP(GET 的 body 沒有
語意,但送得出來)。修正前 `_static` 回 `200` + keep-alive,而那個 body **一個
byte 都沒被讀掉**;`handle_one_request` 接著把殘留的位元組當成**下一個請求的
請求行**來解析,於是:

1. 同一條連線上多出一份基底類別 `send_error` 的 **HTML `400`**——而決策 8 說
   這個伺服器的錯誤**只有** `{"error": …}` 一種形式,那份 HTML 也是我們說出口的
   話。這一條**獨立於 fuzz**:它是決策 8 的破口。
2. `send_error` 之後在**仍有未讀資料**時關 socket,核心發的是 **RST**,對方
   連我們寫好的那個 `200` 一起丟掉 → 用戶端看到 `ConnectionResetError` /
   `BrokenPipeError`,或是一個被截斷的 `200`。在負載下偶發。

舊的 2,000 筆 fuzz(`tests/test_webui_server.py`)body ≤ 2KB 且無換行,所以從來
沒踩到;本票的語料 body 到 70,000 bytes 且是隨機位元組(必然含 `\r\n`),於是
踩了出來。**是本票的語料把一個既有缺陷照出來,不是本票造成的**。

### (a) 修正:收尾搬到唯一的回應出口

```python
undrained = self._undrained_body_bytes()   # 宣告了而沒讀過的 body 有幾個 byte
if undrained and not any(name.lower() == "connection" for name, _ in extra_headers):
    extra_headers = extra_headers + (("Connection", "close"),)
... 寫狀態行 / 標頭 / body ...
if undrained:
    self._drain_request_body()
```

三件事值得記下來:

1. **判斷與收尾都在 `_respond`**,不在呼叫端。原本只有 `_error` 做 lingering
   close,成功路徑就漏了——而「哪些出口要收尾」這種事交給呼叫端自律,下一個新
   出口還是會漏。現在它只有一個實作點。`_error` 的那一行 `_drain_request_body()`
   因此拿掉了(改由 `_respond` 統一做),它的 `Connection: close` 仍然是**無
   條件**的:被擋下的請求我們連 `Content-Length` 都可能沒看懂(`invalid
   Content-Length` 那條),而看不懂長度正是最不該續用這條連線的情況。
   **錯誤路徑的行為一個 byte 都沒變**:修正前 `_error` 無條件呼叫
   `_drain_request_body()`,而那個函式自己對「讀過了」和「看不懂的長度」都早退;
   修正後那兩種情況 `_undrained_body_bytes()` 回 `0`,一樣不呼叫。
2. **沒有殘留 body 的回應一個 byte 都不變。** 收尾是**有條件**的,條件就是「對方
   宣告了而我們沒讀」。沒有這個條件,修正會變成「每個靜態回應都關連線」,而頁面
   載入要 `/` + `/app.css` + `/app.js` 三個請求。
   `::test_a_static_request_without_a_body_still_reuses_the_connection` 守住那個
   沒發生(同一條連線上連打兩個靜態路由,斷言沒有 `Connection` 標頭、
   `will_close is False`);既有的
   `tests/test_webui_crypto.py::test_several_requests_on_one_keep_alive_connection`
   守住 `/api/*` 的那一半。
3. **已知殘留(本票授權半徑之外)**:`Transfer-Encoding: chunked` 的請求沒有
   `Content-Length`,所以 `_undrained_body_bytes` 判不出長度、也框不出 chunk
   邊界。標準庫的 `BaseHTTPRequestHandler` 從頭到尾不支援 chunked 請求
   (`_content_length` 看不到標頭就回 `0`),故那種請求打到 `/api/*` 會被當成空
   body → `400` → `_error` 的無條件 close 收場;打到**靜態路由**則仍可能殘留。
   複審授權的是「宣告了非零 `Content-Length`」這一種,所以這一輪沒有擴到
   chunked——要修的話得決定「讀到超時」與「直接 RST」哪個比較糟,那是一個獨立的
   決定。這條**先於本票存在、本票沒有改動它**,記在這裡供彙整票取用。

### (b) 不靠負載的確定性證人

`tests/test_webui_fuzz.py::test_a_static_200_leaves_no_second_response_on_the_wire`
照複審的重現方式寫:raw socket 送 `GET / HTTP/1.1` + 正確 Host +
`Content-Length: 70700`,body 是每 101 bytes 一個 `\r\n` 的資料,讀到 EOF,
然後斷言

* **access log 恰為 `["GET / 200"]`** —— 這是最確定性的那一條:伺服器有沒有把
  殘留的 body 當成第二個請求,它自己的 log 說得出來;
* 線上只有**一個**狀態行(regex `HTTP/1\.[01] \d{3}`)且是 `200`;
* body **逐 byte**等於 `webui.PAGE_HTML`(這一條同時抓到另一個徵狀:`200` 的尾巴
  被 RST 吃掉);
* 沒有基底類別 `DEFAULT_ERROR_MESSAGE` 的字樣(`Error response` / `Error code`)
  —— 不能掃 `<html`,因為 `GET /` 回的**正是**一份 HTML 頁面;
* 有 `Connection: close`(授權項 (a) 的機制本身)。

**修前即紅,實測過**:把 `_undrained_body_bytes` 換成 `lambda self: 0`
(= 修正前的行為)跑這一條 →
`AssertionError: access log 不只一行——殘留的 body 被當成下一個請求了:
['GET / 200', '- / 400']`。沒有負載、沒有時序假設、沒有 sleep。

### (c) fuzz 迴圈接住連線層的例外

`_send_plan(srv, plan, index)` 把 `send` 包起來,`OSError`(`ConnectionResetError`
/ `BrokenPipeError`)與 `http.client.HTTPException`(`RemoteDisconnected` /
`BadStatusLine`,串流錯位的另一種徵狀)一律轉成帶 `index` 與 `_describe(plan)`
的 `AssertionError`。seed 固定,所以有 index 就重現得出來。兩條 10,000 筆的迴圈
都走它。

(複審只點名 `OSError`;這裡多接了 `HTTPException`,因為 `BadStatusLine` 不是
`OSError` 而它正是「下一個回應讀到的是上一個的殘渣」最直接的徵狀——漏接它等於
留一條同樣查不下去的裸例外路徑。)
