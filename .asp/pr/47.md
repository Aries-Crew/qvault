# fix(webui): #47 一條連線只有一個關閉者——停止信號落在 `t.start()` 之後時,在途回應不再丟失

Closes #47

停止信號落在 `ThreadingMixIn.process_request` 的 `t.start()` 剛回來、工作執行緒
已經拿到連線的那一刻,標準庫 `socketserver.BaseServer._handle_request_noblock`
的**裸 `except:`** 會由**主執行緒**對那條**在途連線**呼叫 `shutdown_request`,
回應整份丟失(客戶端看到 `RemoteDisconnected`,連狀態行都沒有),而 access log
可能已經記下一個 `200`。這違反複審 M1 的承諾:**已接收的請求要完整回應後才停**。

修法是把連線的**關閉所有權**交給工作執行緒:`WebUIServer.process_request` 在
`super().process_request(...)`(含 `t.start()`)之前把連線記進 `_handed_off`,
在這個集合裡的連線,主執行緒的 `shutdown_request` / `close_request` **一律無
作用**;唯一的關閉者是 `process_request_thread` 的 `finally`(它先把所有權交回
再走 `TCPServer.shutdown_request` 原本那條 `SHUT_WR` + `close`)。所以那個窗口裡
**沒有人**有權關它——不是「窗口變窄了」,也不靠任何逾時或調參。

產品改動只有 `qvault_core/webui.py` 一個檔(`+113`,全部是新增:四個覆寫 + 兩個
私有小工具 + 兩段狀態,其餘是說明為什麼的 docstring);既有函式一行未改,
`UI_DRAIN_SECONDS` / `503` / exit code 的行為零改動;核心四檔(`aead` /
`container` / `kek` / `vault`)與 `cli.py` 零改動;相依未動。

## 根因:標準庫的哪三段

**①** `socketserver.ThreadingMixIn.process_request` 以 `t.start()` 作**結尾**:

```python
    def process_request(self, request, client_address):
        """Start a new thread to process the request."""
        if self.block_on_close:
            vars(self).setdefault('_threads', _Threads())
        t = threading.Thread(target = self.process_request_thread,
                             args = (request, client_address))
        t.daemon = self.daemon_threads
        self._threads.append(t)
        t.start()
```

而 `threading.Thread.start` 的最後一行是 `self._started.wait()`——主執行緒在那裡
**等**,而信號正是在這種等待裡被遞送(我們的 handler 拋例外,PEP 475 的重試不
適用)。那一刻工作執行緒**已經拿到連線**,所以窗口 ≈ 那次 `Event.wait()` 的整段
時間,不是一個 bytecode 的縫。

**②** `socketserver.BaseServer._handle_request_noblock` 把那個呼叫包在:

```python
            try:
                self.process_request(request, client_address)
            except Exception:
                self.handle_error(request, client_address)
                self.shutdown_request(request)
            except:
                self.shutdown_request(request)
                raise
```

`cli._Stopped`(SIGTERM / SIGHUP)與 `KeyboardInterrupt`(SIGINT)都是
`BaseException`——前者**刻意**如此(`test_the_stop_exception_is_not_an_exception_so_socketserver_cannot_eat_it`
釘著,否則信號會被第一支 `except Exception` 吞掉),所以走的是**第二支**:
`self.shutdown_request(request)` 關掉的是工作執行緒正在用的那條 socket。

**③** 而 `ThreadingMixIn.process_request_thread` 的

```python
        finally:
            self.shutdown_request(request)
```

本來就會關同一條連線。也就是說同一條連線有**兩個**關閉者,其中一個(主執行緒)
可能在工作執行緒還沒寫出一個 byte 的時候就關。修法因此不是「關得晚一點」而是
**取消其中一個關閉者**。

**為什麼不靠逾時**:`_handed_off` 是一個布林事實,不是一個期限——主執行緒在那
一刻對那條連線**沒有關閉權**,與機器忙不忙、CPU 幾核、worker 睡多久都無關。
也因此不需要覆寫任何私有方法(`_handle_request_noblock` 一個 byte 都沒碰):
覆寫的四個都是 `socketserver` 的公開介面。

**票文寫的 `qvault_core/webui.py:1390`**:改動前的本工作卷那一行是
`class WebUIServer(ThreadingHTTPServer):`(本專案的交界;本次新增往上推了
docstring 一節,所以那個行號在 head 上已經不指同一行),票文自己與
supervisor 留言 ④ 都把它標成「線索而非事實」。真正的根因在上面那三段標準庫,
修正落在 `WebUIServer` 對它們的覆寫(`:1431`、`:1490`–`:1581`)。

這一格把 `ThreadingMixIn.process_request` 換成「丟 `RuntimeError`(起不了
執行緒)」:工作執行緒**根本沒起來**,沒有人會跑 `process_request_thread` 的
`finally`。延後若不撤掉,那條連線的 fd 會留到行程結束(而 `ui` 是個跑很久的

已經在跑,那正是本修正要保護的那一刻(`process_request` 的 docstring 寫明了這個
不對稱)。

## 已知限制

- **「負載下 20 次」的負載這一半沒驗**(見 AC-2 那一列與留言 ② 的處置):worker
  無法保證宿主負載。本票改用注入式的**確定性**重現取代機率式的重現——那也是
  AC-1 要的東西;機率式的那一半留給人側 / CI 的複核。
- **延後關閉的覆蓋面是「交給工作執行緒之後」**。`verify_request` 不通過、
  `get_request` 自己失敗、或 `process_request` 還沒被呼叫到的那些連線,照舊由
  標準庫關(本票沒碰那些路徑)。真正被保護的只有「已經有一條工作執行緒對它負責」
  的連線——那也正是會丟回應的那一種。
- **`_handed_off` 的清理靠兩條路徑**(工作執行緒的 `finally`、`process_request`
  的 `except Exception`)。信號路徑下若直譯器在工作執行緒跑完 `finally` 之前就
  結束,集合裡會留一個條目——行程正在消失,所以那不是洩漏;真正的 fd 由 OS 收。
  集合的大小上限是「同時在途的連線數」,不隨時間長大。
- **本票不碰 `UI_DRAIN_SECONDS` 的語意**:退出時的等待仍然是**有界**的緩解
  (決策 12 的 5 秒),逾時仍會印那句警告。本票修的是「等待期間/之前那一刻
  **不要有人把連線關掉**」,不是「等更久」。
