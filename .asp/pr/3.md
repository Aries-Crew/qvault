## 做不到 / 打了折的,逐條說明

### 1. [M3] 的後半「`encrypt_file` 一律寫 15/8/1」**不在本票範圍**,只能先架好門

`encrypt_file` 是 #4 的 `vault.py`,本票沒有這個檔案。本層能做的是讓 [M3] 變成
**結構問題而不是自律問題**,已全部做掉:

- 正規建構子 `ScryptKEK(pw, salt)` 的預設值是簽章上的字面值 15/8/1,且只接受
  正規界限 `log2n ∈ [14,22]` / `r ∈ [1,32]` / `p ∈ [1,16]`(解密舊檔要照 header
  走,決策 7,故不能寫死;但低於下界一律拒絕)。
- 測試想跑快必須改用 `ScryptKEK.insecure_for_tests(...)`——名字裡就寫著
  insecure,不可能是手滑。
- `test_production_code_never_uses_the_insecure_hatch` 掃 `qvault_core/**/*.py`,
  除 `kek.py` 外只要有第二處提到 `insecure_for_tests` 或 `_allow_insecure_params`
  就失敗。**#4 一旦想借低參數把 `encrypt_file` 跑快一點,這條測試當場死。**

留給 #4 的仍是一條「`encrypt_file` 寫進 header 的 kdf_* 必須是 15/8/1」的斷言
(header 的預設值已經是 15/8/1,`test_header_default_cost_fields_match_the_kek_defaults`
把兩邊釘在一起)。

### 2. wrap 沒有「官方 KAT」——隨機 nonce 不可能有固定輸出

AC 沒要求,但這裡說明為什麼不像 #2 那樣附 NIST 向量:`wrap()` 每次自產隨機
nonce,同輸入不同輸出,**KAT 在定義上不存在**。改用兩條等效的硬證據:

- **KDF 層**:RFC 7914 §12 的三組官方向量(`_scrypt` 的參數順序、dklen 截斷全釘死)。
- **AEAD 層**:`test_wrap_layout_is_nonce_then_ct_then_tag` 固定 nonce 後,期望值由
  `cryptography` 的 `AESGCM` **直接算**(不經 `qvault_core.aead`),等於拿第二條
  獨立路徑對帳佈局與 AAD;而 `AESGCM` 本身的正確性由 #2 的 5 組 NIST KAT 保證。

### 3. 比 AC 嚴的四處(都是「合理選擇也會蓋出洞」那一類,故選嚴的)

1. **`kem_id` 是抽象成員**。AC 的 [L] 只要求「缺 `wrap` 的子類 → `TypeError`」;
   本實作連缺 `kem_id` 都 `TypeError`。理由:`kem_id` 要寫進 header,漏掉它的 KEM
   會寫出一個**沒人讀得回來**的檔,而那個錯誤要到解密時才發作。若 QA 認為子類
   不該被強制,拿掉 `KeyEncapsulation.kem_id` 上的 `@abstractmethod` 一行即可,
   `ScryptKEK` 完全不受影響。
2. **passphrase 只收 `str`,不收 `bytes`**。`bytes` 沒有「NFC 正規化」可言,收了
   就等於開一條繞過決策 18 的路,同一個密碼於是有兩種 KEK——症狀是「跨平台密碼
   錯誤」,沒人會往正規化去猜。
3. **UTF-8 編碼失敗自己接住**。孤兒代理對(Windows argv 經 `surrogateescape`
   進來)會讓 `UnicodeEncodeError` 把**出錯的那個字元印進訊息**,那是密碼的一部分,
   直接違反鐵律 5。改丟不帶內容的 `ValueError` 並 `from None`。
4. **金鑰包在 `_SecretBytes` 裡,且禁止 pickle**。`__repr__` 管得住 `repr(kek)`,
   管不住 `repr(vars(kek))` 與 `logging.debug("%r", kek.__dict__)`——[H4] 的測試
   正是打 `repr(vars(kek))` 那一發,所以閉嘴的責任必須落在**值**上。pickle 一併
   封掉:把 KEK 醃進 cache 檔就是「金鑰落地」,而 pickle 不會問過任何人。

### 4. 成本參數與 salt 的錯誤型別是 `QVaultFormatError`,不是 `ValueError`

沿用 #1/#2 的同一條判準——**看這個值從哪裡來**:

- `log2n`/`r`/`p`/`salt` 在**解密路徑上來自 `.qvt` header**,是攻擊者可控的欄位值,
  越界屬「格式壞掉」。`deserialize` 已擋過一輪(決策 15),本層是第二道:KDF 參數
  是唯一一組「在 tag 被驗證之前就要拿去配置記憶體」的值(`log2n=63` → `Scrypt(n=2**63)`
  → OOM),兩道都便宜,少一道就得賭呼叫端沒繞路。`test_out_of_range_cost_parameters_raise_before_the_kdf_runs`
  以 monkeypatch 斷言 **KDF 從未被呼叫**。
- `dek` 來自 `gen_dek()`,**不是**檔案,長度/型別錯是呼叫端的 bug → `ValueError`
  (與 #2 對 `key`/`nonce` 的處理同一條)。報成 `QVaultDecryptError` 會讓 CLI 把
  程式 bug 說成「密碼錯誤」。

### 5. `unwrap` 的長度不符是 `QVaultFormatError`,不是 `QVaultDecryptError`

`wrapped_dek` 是**定長 60B 的欄位**(#1 的 `_check_params` 已保證),長度不對代表
header 沒被檢查過就進來了,是格式問題。這不構成 oracle:長度是明文寫在檔案裡的
公開資訊,攻擊者本來就看得到,而**所有真的「解不開」的路徑**(錯密碼、錯 salt、
錯參數、改任一 byte)型別與訊息逐字相同([M4] 的測試守著)。

若 QA 要求統一成 `QVaultDecryptError`,改動是 `unwrap` 的一行 + 兩個測試的
`pytest.raises` 型別,無其他相依。

### 6. `kek.py` 不 import `container.py`,常數各存一份

ADR 的相依圖裡 `container` 與 `kek` 是**兄弟**(`cli → vault → {container, aead, kek}`),
互相 import 就成了環。代價是 `SALT_LEN` / `KEM_ID_SCRYPT` / `WRAPPED_DEK_LEN` /
KDF 三組界限在兩處各有一份;沿用 #2 的辦法,`test_constants_agree_with_container`
把兩份數字逐一釘在一起(順帶再對 `WRAPPED_DEK_LEN == 12 + 32 + 16`)。

`WRAPPED_DEK_LEN` 與 `KEM_ID_SCRYPT` **刻意不**轉出到套件根:`container` 有同名
同值的常數,兩個都放上去只會製造「這是誰的 60?」的疑問(#2 對 `NONCE_LEN` 的
同一條理由)。要用請 `from qvault_core.kek import ...`。

### 7. 沒做的(不是打折,是不在本票範圍)

- **salt 怎麼來**:[C1]「每檔 `secrets.token_bytes(16)`」是 #4 的事。本層只做到
  **不給 salt 預設值**——預設值就是常數 salt,而常數 salt = 全世界共用一把 KEK
  (決策 10)。`test_signature_defaults_are_literal_15_8_1` 順帶斷言
  `salt` 沒有預設值。
- **金鑰歸零 / 記憶體擦除**:Python 的 `bytes` 不可變,無法可靠擦除;ADR 威脅模型
  明列「記憶體取證」為**不防**。`_SecretBytes` 擋的是**印出去**與**醃出去**,
  不假裝擋得住 RAM dump。
- **密碼強度政策**:決策 8「P0 不強制強度」,故空密碼是**合法**輸入
  (`test_roundtrip_over_passphrase_shapes[""]` 明寫這個行為)。
