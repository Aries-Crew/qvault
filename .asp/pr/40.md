## 這張票在修什麼

兩件事,都繞著 `_serve` 退出序列裡那個 `with _signals_deferred():`:

1. **測試的時間預算太緊**(AC-1):`test_a_second_stop_signal_does_not_abandon_the_in_flight_request`
   在主管層宿主連跑 20 次紅 3 次,死因一律是 `qvault: gave up after 3s waiting
   for a request still running`。慢請求的在途窗口是 2.0 秒,產品期限
   `UI_DRAIN_SECONDS` 是 3.0 秒——名目餘裕 1 秒,排程抖動超過就紅。而那條測試
   斷言的是「第二個停止信號有沒有把等待丟掉」,**不是**「3 秒夠不夠」:它紅在
   一件自己沒有在驗的事上。獨立複審判定為測試時間預算問題,非產品缺陷。
2. **PR #35 引入的一個退步**(AC-2):#35 處置 info 時把 `_report(warning)` 搬進
   `with` 區塊**內**。信號落在 `_signals_deferred.__enter__` **完成之前**時,
   例外是從 `with` 那一行冒出來的——body 一次都沒跑,區塊內的 `finally` 也就
   沒跑,於是那一行「輸出目錄可能留下明文 `.qvault-*.part`」的警告**不印**。
   #24 之前那一格會印;#35 之後變靜音。

## 改了什麼

### `qvault_core/cli.py`(+1 層 `try/finally`,其餘是註解)

```python
        warning: str | None = (f"stopped waiting …{_PART_FILE_WARNING}")
        reported = False
        try:
            with _signals_deferred():
                try:
                    ...                      # 宣布停止 → 關 listen socket → 等在途 → 等瀏覽器
                finally:
                    reported = True          # 旗標先立再印
                    if warning is not None:
                        _report(warning)
        finally:
            if not reported and warning is not None:
                _report(warning)
```

- **兩層都留,不是把內層搬出來**:內層那個印正常路徑——`_report` 是一次 I/O,
  處置還原之後才印的話,信號落在那一刻就會把它吃掉(#24 複審第 2 輪的 info
  要的就是這個性質,本票不打算把它退回去)。外層只補一格:`__enter__` 自己被
  信號打斷、內層 `finally` 一次都沒跑到的那一格。
- **`reported` 旗標保證不會印兩次**:旗標在 `_report` **之前**立起來。重複印一
  行警告會讓讀的人以為有兩份在途工作;`test_giving_up_on_a_long_request_says_so_and_still_exits_zero`
  的 `len(lines) == 1` 守著這一刀。
- **行為邊界**:`warning` 的計算、`UI_DRAIN_SECONDS` 的值、吞後續信號、503、
  exit code 全部沒動。唯一可觀察的差異就是裁定圈定的那一格:原本靜音,現在
  印一行既有的 `stopped waiting …`(訊息字串也沒變,是 #24 就有的那句)。

### `tests/test_cli_ui.py`

- **新常數**:`STRICT_DRAIN_SECONDS = 8.0`(注給退出路徑的等待期限)、
  `STRICT_BODY_SECONDS = 2.0`(在途窗口)、`STRICT_JOIN_SECONDS = 20.0`
  (收執行緒的期限)。每個都寫了「為什麼是這個數」。
- **`_ExitTiming`**(新):一個同時做「注期限」與「蓋時間戳」的小夾具。
  - `monkeypatch.setattr(cli, "UI_DRAIN_SECONDS", 8.0)`——`_serve` 是在
    `wait_until_idle(UI_DRAIN_SECONDS)` 那一刻才讀這個模組屬性(沒有 import 時
    綁名、沒有預設參數把它凍住),故 monkeypatch 有效;實測印出來的
    `實際傳進 wait_until_idle=8.0` 就是那個證據。
  - 三個 monotonic 時間戳:`sent`(標頭真的送出去那一刻,走新加的 `on_sent`
    鉤子,不是等事件的那一端自己量——那會晚一個輪詢間隔)、`開始等待`
    (退出路徑第一次 `timeout` 非 0 的 `wait_until_idle`;測試自己輪詢用的
    `wait_until_idle(0)` 不算)、`work_finished`(**先蓋戳再減計數**:戳要代表
    工作做完那一刻,先跑標準庫那半的話戳會晚於「等待結束」,時間線讀起來
    因果顛倒)。
  - 失敗訊息長這樣(下面那次實測紅的原文):

    ```
    ;monotonic:sent=1771783.019,開始等待=1771783.026,work_finished=1771785.020
    ;work_finished−開始等待=+1.994s
    ;期限=注的 8s/cli.UI_DRAIN_SECONDS=8s/實際傳進 wait_until_idle=8.0
    ```

- **`_InProcessUI.WATCHDOG_SECONDS` 10.0 → 15.0**:AC 第 3 條的 5 秒 + 最壞情況
  的退出預算(注的 8.0 + `UI_BROWSER_SECONDS` 0.5)= 13.5 秒。不同步調大的話,
  看門狗會在「產品還在合法等待」時開火,而死因會寫成「`ui` 沒有自己停下來」
  ——完全看不出是測試自己的期限太短。
- **`check()` 與 `caller.join` 的期限**:`_InProcessUI(monkeypatch,
  join_timeout=...)`,預設仍是 `EXIT_TIMEOUT`(5 秒,那是 AC 給**真行程退出**
  的預算),嚴格那兩條傳 `STRICT_JOIN_SECONDS`。HTTP 呼叫端要在退出路徑等完
  之後才把回應讀完,用 5 秒量這一段就是下一個太緊的期限。
- **新測試 `test_a_signal_before_the_deferral_is_installed_still_warns`**
  (`KeyboardInterrupt` / `_Stopped` 兩格):把 `cli._signals_deferred` 換成
  `_InterruptedOnEnter`(`__enter__` 直接拋),斷言 exit 0、stderr **恰好一行**
  `qvault: stopped waiting …; a partial .qvault-*.part file may be left …`、
  無 `Traceback`。用替身而不是去打真窗口:那是幾微秒寬的競態,打中靠運氣,
  而這條驗的是 `_serve` 外層那個 `try/finally`(`_signals_deferred` 自己另有
  `test_the_exit_path_defers_stop_signals_and_restores_them`)。手法與既有的
  `test_abandoning_the_wait_still_warns_about_the_part_file`(把
  `wait_until_idle` 換成「直接拋」)同一套。這條路徑走不到產品的
  `server_close()`,故測試自己把 listen socket 收掉,不漏給後面的測試。

## 那次滿載紅掉的根因(不是本票的 AC,但要交代清楚)

第 11 回紅的是 `ui.check()` 的「驅動執行緒出錯」那條斷言,不是期限:

```
驅動執行緒出錯(在途請求被砍掉時會是 RemoteDisconnected):
[RemoteDisconnected('Remote end closed connection without response')]
;stderr='POST /api/inspect 200\nPOST /api/inspect 400\n'
;monotonic:… ;work_finished−開始等待=+1.994s ;期限=注的 8s/…/實際傳進 wait_until_idle=8.0
```

三項事實:**①** 在途工作在開始等待後 1.994 秒就做完了(期限 8 秒,沒有逾時,
stderr 也沒有 `gave up` / `stopped waiting`);**②** 伺服器端 access log 已經記了
`POST /api/inspect 200`——工作做完、回應也送出去了;**③** 客戶端拿到的是
`RemoteDisconnected`,回應**丟了**,後面還多一行 `400`(同一條連線接著被當成
新請求讀)。

這正是票文末尾「後續候選」記的那一格:信號落在 `t.start()` 剛結束、工作執行緒
已計入在途的那一刻,標準庫 `socketserver._handle_request_noblock` 的裸 `except:`
會對那條**在途**連線 `shutdown_request`,工作照做完但回應丟失。CPU 吃滿時主執行
緒在 `t.start()` 之後被排程器停住的那段窗口會被拉寬到足以被第一個信號打中。

- **它不是本票引入的**:第一個信號的發送時機一個字都沒改(仍是「確認請求被數進
  在途之後」),期限注入只影響**等待多久**,不影響那個窗口。
- **本票不修它**:票文明寫「不在本票 AC,記錄供參」,主管層的裁定也把 `cli.py`
  的改動圈定在 AC-2 那一處;修它要動 `webui.py`(覆寫 `process_request` /
  `handle_error` 那一層)。
- 若要讓「滿載 20/20」在 CI 上成立,得先處置那一格;本票把它的**死因**變得
  一眼可辨(時間戳 + 期限 + access log 都在同一條失敗訊息裡),這是這一輪能做到
  的部分。

## 人側複核項(worker 能力上限,比照 ROADMAP P3 的條款)

- **「有負載的機器連跑 20 次零紅」**:worker 只能在自己的容器裡近似負載,無法
  重現主管層那台宿主的抖動形狀。上面給的是兩組實測數字(無負載 20/20、滿載
  19/20 且零次紅在期限),**那台宿主上的 20 回請人側再跑一次**——要看的是
  「有沒有再出現 `gave up after …`」,而不是「有沒有紅」:後者可能是上一節那
  一格。
- **gitleaks**:容器裡沒有這個工具,交 CI。
