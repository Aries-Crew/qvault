## 決策 12 沒說的那兩件事,我怎麼決定的

票上留言建議 ①「也建議寫明乾淨退出時 stdout / stderr 要不要留一行」——決策 12
只要 exit 0 + 不吐 traceback,沒說。本票的選擇與理由:

- **乾淨退出什麼都不印**(stdout 與 stderr 都是空的,測試逐字斷言 `err == ""`)。
  stdout 的那一行是給管線與瀏覽器讀的,多一行就多一個要解析的東西;而
  `qvault ui | head -1` 這種用法要能動。
- **`SIGTERM` 用「丟例外」而不是 `server.shutdown()`**:signal handler 跑在主
  執行緒上,而 `shutdown()` 會等主執行緒的 `serve_forever` 迴圈回應它——那是一個
  必死的死鎖。標準庫對 `SIGINT` 的做法就是丟 `KeyboardInterrupt`,這裡照抄
  (`_Stopped`),好讓兩條退出路徑收在同一個 `except` 裡。
  非主執行緒裝不了 handler(`signal.signal` 丟 `ValueError`)時不視為錯誤,照樣
  服務、只是少掉 `SIGTERM` 這條捷徑——`test_serving_from_a_side_thread_still_works_without_a_handler`
  守著(函式庫呼叫端把 `cli.main` 丟到 thread 裡跑是合法用法)。
- **順序**:先 `make_server`(綁 socket)→ 印那一行 → 開瀏覽器 → `serve_forever`。
  先綁才知道 `--port 0` 配到哪個埠,也才能在埠被占時「什麼都還沒印」就乾淨失敗;
  而 socket 在 `make_server` 裡就已經 listen,所以瀏覽器比 `serve_forever` 早到
  只會排在 backlog 裡,不會吃到連線被拒。
- **`server_close()` 在 `finally`**:`ui` 可能是一個跑很久的行程,不能靠行程結束
  來收 listen socket(`test_the_server_is_closed_before_main_returns` 驗 `main`
  還沒回來之前 fd 就關了)。

## 人側驗收項(worker 能力上限,ADR-002 決策 14)

`webbrowser.open` 真的開起一個瀏覽器、以及頁面在真瀏覽器裡的互動,worker 驗不到
(沙箱無瀏覽器)。本票驗到的是「`open` 被呼叫一次、參數等於印出的那一行」與
「那一行上的 port / token 真的能通 `/api/inspect`」;**合併前的人側驗收**建議:
`qvault ui` → 瀏覽器自動開啟 → 網址列的 `#token` 立刻被 `history.replaceState`
抹掉(#23)→ 三個表單各跑一次 → 終端 Ctrl-C → exit 0 且頁面後續請求全部失敗。
