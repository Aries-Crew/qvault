## 對 AC 第 9 條的誠實交代:`cli.py` 多動了模組 docstring

`cli.py` 的 diff 除了「`ui` 子解析器 + `_cmd_ui` + 它用到的常數 / signal 工具 +
三個標準庫 import + `from .webui import …`」之外,**還改了模組 docstring 三處**:

1. 首行 `qvault encrypt / decrypt / inspect` → 加上 ` / ui`。
2. 相依圖那一句補「自 #24 起另有 `cli → webui`(ADR-002 決策 13 定的方向)」,
   「本檔只做四件事」→「五件事」。
3. 「本層不做的事」補一項:**`ui` 不決定任何 Web UI 的事**——綁哪個位址、token
   怎麼來、哪些門要擋全在 `webui.py`,所以這裡沒有 `--host` / `--bind`。

判讀:AC 第 9 條的用意是**改動半徑**(不要順手重構 `cli.py` 的其他部分),而這
三處都是在描述本票新增的那個子命令;把一個新子命令加進去卻讓檔頭繼續寫「只做
四件事、相依圖只有 `cli → vault`」,等於留一份當場就過期的文件,而本 repo 的
docstring 是被測試與複審當真的(`cli.py` 的檔頭正是 [M7] 白名單那條規矩的住所)。
行為、既有函式、既有訊息**一個字未動**。若複審認為 AC 第 9 條要逐字讀(連
docstring 都算改動),回退這三處只需一個 revert-hunk,不影響任何測試。

## 測試改動(`test-change-ack:`)——主管層裁定的那一格

`tests/test_webui_server.py::test_the_core_four_and_the_cli_do_not_import_webui`
的 parametrize 從 `["aead.py", "kek.py", "container.py", "vault.py", "cli.py"]`
收成前四個,函式更名為 `test_the_core_four_do_not_import_webui`,docstring 記下
裁定。**這正是票文「主管層層裁定」允許、也只允許的那一條**:它斷言的是

(本票要落的那條邊)直接矛盾。

守:`qvault_core/__init__.py` 既不 import `cli` 也不 import `webui`(`ast` 驗),

扛伺服器的只有 `qvault_core.cli` 這一個模組(以及 `qvault` 這個執行檔),函式庫
用法的 import 清單一個字未變。另加 `test_the_cli_takes_exactly_two_names_from_webui`
守**邊的粗細**:`cli` 只從 `webui` 取 `LOOPBACK` 與 `make_server` 兩個名字,

### F2 ─ 信號裝太晚(AC 第 3 條判 fail 的直接成因)

- **修正前**:`SIGTERM` 與 `_sigterm_as_exception` 之間有一段空窗期——印網址、
  開瀏覽器都在它之前,而 `webbrowser.open` 可以**一走就不回來**。實測
  `SIGTERM → rc=-15`(預設處置當場殺掉)、`SIGINT → rc=130` + `qvault: interrupted`
  (冒到 `main()` 的共用出口)。
- **修正**:`_cmd_ui` 現在只做一件事——把**整個**本體(`_serve`:綁 socket、印、
  開瀏覽器、服務、收乾淨)包進 `with _signals_as_exit()` 並在外層接
  `(KeyboardInterrupt, _Stopped)`。`main()` 的共用分支仍然一個字未動。
- **修正後實測**:`SIGTERM` / `SIGINT` / `SIGHUP` 三種在阻塞瀏覽器下皆 `rc=0`、
  `0.51s`、stdout 只有那一行。
- **守門人**:`test_a_signal_during_a_blocking_browser_still_exits_zero`(三格)。
  變異「把信號處置改回只包 `serve_forever`」→ 殺。

### F3 ─ 阻塞的瀏覽器把服務擋住

- **修正前**:`webbrowser.open` 在主執行緒上呼叫,它不回來 → `serve_forever`
  永遠輪不到。實測:對印出來的網址打 `/api/inspect` **逾時**——使用者拿到一個
  印了網址卻完全不回應的伺服器。
- **修正**:`_open_browser` 丟到一條 **daemon 執行緒**上(例外一律吞掉:從執行緒

  退出時 `join(timeout=UI_BROWSER_SECONDS=0.5)`——等不到也不擋行程結束,等這半秒
  只是為了「Ctrl-C 來得很快」時瀏覽器仍開得成(AC 第 5 條那兩條 in-process 測試

- **守門人**:`test_a_blocking_browser_does_not_keep_the_server_from_serving`。

### F1 ─ 中斷會留下 `.qvault-*.part`(明文片段)

- **成因**:`vault` 的寫法是「寫 `.qvault-*.part`(0600、同目錄)→ `os.replace`」,
  失敗時 `finally` 把它 unlink 掉。純 CLI 因此**沒有**這個問題:解密跑在主執行緒
  上,Ctrl-C 把堆疊解開、`finally` 清得掉。`ui` 不一樣——工作跑在 **daemon** 連線
  執行緒上,直譯器一結束就被砍掉、`finally` 不跑,於是中途被打斷的解密把一個
  明文片段留在 `out_dir` 裡。**是 `ui` 這個生命週期把它變出來的**,所以由 `ui` 收。
- **修正**:`webui.WebUIServer` 數「在途的 `/api/*` 請求」(`work_started` /
  `work_finished` 包在 `_handle` 的 `/api/*` 分支外,連被擋下與丟例外的都算),
  `qvault ui` 退出時先 `server_close()`(不再收新連線)再
  `wait_until_idle(UI_DRAIN_SECONDS=3.0)`。
  - 為什麼不是「等所有連線執行緒」:HTTP/1.1 keep-alive 下,開著頁面的瀏覽器會
    讓一條執行緒**活著但閒著**,用執行緒當判準的話每次 Ctrl-C 都要白等滿預算。
    `test_a_static_request_is_not_counted_as_work` 守這一刀。
  - 為什麼不是改 `vault.py`:核心四檔零改動是本票的共同範圍條款;真正把這個窗口
    **關掉**(而不是縮小)要在那一層做(例如 `O_TMPFILE` + `linkat`,檔案在完成
    之前根本沒有名字),那是另一張票的事,不在本票做。
- **兩條路都用 QA 的 F1 場景實測過**(真子程序、真 HTTP、真解密,中途送 `SIGINT`):

  | 在途的解密 | 退出耗時 | rc | `out_dir` 結果 | stderr |
  |---|---|---|---|---|
  | 512 MiB(解密 ≈ 1.3 秒,**在預算內**) | 1.11 秒 | 0 | 只有**完整**的 `big.bin`(512 MiB),**沒有** `.part` | 只有 access log,無 `Traceback` |
  | 2 GiB(解密 ≈ 6 秒,**超過預算**) | 3.09 秒(< AC 的 5 秒) | 0 | 留下 `.qvault-xxxxxxx.part`(`0600`) | access log + **那一行警告**,無 `Traceback` |

  修正前這兩格都是「立刻退出 + 留下 `.part`」。
- **誠實的邊界**:這是**有界的緩解,不是保證**。超過 3 秒的在途工作仍會被留下
  (上表第二列就是那一格),此時 `ui` 會多印一行
  `qvault: gave up after 3s waiting for a request still running; a partial .qvault-*.part file may be left in its output directory`
  ——使用者有權知道該去看一眼。`SIGKILL`、斷電一樣會留。
- **為什麼那行警告不告訴你是哪個目錄**:`out_dir` 來自請求 body,而 ADR-002 決策 9
  是「伺服器不記 body」——access log 只記 method / path / 狀態碼。為了這句警告把
  使用者的路徑寫到 stderr,等於在決策 9 上開一個新的洞;訊息因此只說檔名長什麼
  樣子(`.qvault-*.part`),目錄是使用者自己剛剛在表單裡填的那個。
- **守門人**:`test_an_in_flight_request_is_finished_before_the_process_exits`
  (子程序 + 真 HTTP,用「body 慢慢送」造出可控的在途窗口,不需要一個大到要跑
  好幾秒的檔案)、`test_the_server_knows_when_api_work_is_in_flight`、
  `test_a_real_api_request_shows_up_as_in_flight`、
  `test_giving_up_on_a_long_request_says_so_and_still_exits_zero`。
  變異「拿掉 `wait_until_idle`」→ 殺(2 條);變異「靜態請求也計數」→ 殺。

### 補修 ─ F3 的修正自己帶進來的一個窗口(本票測試在全套裡抓到的)

`qvault ui` + Ctrl-C **在極少數時候**會回 `exit 1` 並印
`qvault: internal error (RuntimeError)`——使用者按了 Ctrl-C,拿到的卻是「我們有
bug」,而那正是 AC 第 3 條禁止的 `returncode != 0`。

- **怎麼發現的**:全套跑一次,`test_a_signal_during_a_blocking_browser_still_exits_zero[SIGINT]`
  紅了一次(`rc=1`、`err='qvault: internal error (RuntimeError)'`)。它之前連跑兩次
  都綠——因為那是一個**幾微秒**的競態,不是穩定失敗。
- **成因**:F3 的修正寫成
  `browser = threading.Thread(...)` → `browser.start()`。信號若落在這兩行**之間**
  (或落在 `start()` 回來之前),退出路徑的 `browser.join(...)` 會對一條還沒 start
  的執行緒丟 `RuntimeError: cannot join thread before it is started`;它從 `finally`
  冒出去、**取代**原本的 `KeyboardInterrupt`,於是 `main()` 的 `except Exception`
  把它翻成 `internal error (RuntimeError)` + exit 1。
- **修正**:先 `start()`、**成功之後**才把它記進 `browser`。`browser` 非 `None`
  ⇒ 它一定 start 過,窗口就不存在了。
- **守門人**:`test_an_interrupt_while_the_browser_thread_starts_is_still_exit_zero`
  ——把 `Thread.start` 換成「當場丟 `KeyboardInterrupt`」,等價於信號正好在那一刻
  到達,**確定性**地蓋住這個窗口(子程序那條只能靠運氣撞到)。變異「把指派搬回
  `start()` 之前」→ 殺。
- **順帶把兩條賭時序的測試改掉**:`test_an_in_flight_request_is_finished_before_the_process_exits`
  與 `test_a_real_api_request_shows_up_as_in_flight` 原本用固定的 `sleep` 賭「執行緒
  起來 + 連線 + 送標頭」來得及;改成由 `_slow_api_request` 在**標頭送出之後**
  `Event.set()`,呼叫端等事件、並把在途窗口從 0.4–0.6 秒拉到 1.5–2.0 秒。
  (全套那一次另有一條在隨機順序下偶發紅掉、我沒抓到名字的;這兩條是唯二靠
  `sleep` 賭時序的,改掉之後 12 個隨機種子連跑全綠。)

### info ─ `_signals_as_exit` 的哨兵一值兩用

`None` 原本兼了兩種意思。現在分開:`signal.signal` 丟 `ValueError`(非主執行緒,

`test_a_signal_we_could_not_install_is_not_restored`)。

## 決策 12 沒說的那幾件事,我怎麼決定的

票上留言建議 ①「也建議寫明乾淨退出時 stdout / stderr 要不要留一行」——決策 12
只要 exit 0 + 不吐 traceback,沒說。本票的選擇與理由:

- **乾淨退出不印告別詞**。stdout 的那一行是給管線與瀏覽器讀的,多一行就多一個
  要解析的東西;`qvault ui | head -1` 這種用法要能動。
  **兩個如實的但書**(QA 第 2 輪點名修正的措辭):
  ① stderr 不是「一定空的」——`webui` 的 access log(決策 9:只有 method、path、
  狀態碼)本來就寫在 stderr,所以跑過請求的 session 退出時 stderr 裡會有那幾行;
  AC 要的是「不含 `Traceback`」,那條恆成立。② 放棄等待在途工作時會多一行
  `qvault: gave up after 3s …`(見 F1)——那報的是磁碟上可能多了一個明文片段,
  值得一行。沒有請求、也沒有逾時的那種 session,stderr 仍然逐字是空的
  (`test_a_signal_stops_it_within_five_seconds_with_exit_zero` 斷言 `err == ""`)。
- **信號用「丟例外」而不是 `server.shutdown()`**:signal handler 跑在主執行緒上,
  而 `shutdown()` 會等主執行緒的 `serve_forever` 迴圈回應它——那是一個必死的死鎖。
  標準庫對 `SIGINT` 的做法就是丟 `KeyboardInterrupt`,這裡照抄(`_Stopped`),好讓
  每條退出路徑收在同一個 `except` 裡。非主執行緒裝不了 handler 時不視為錯誤,照樣
  服務、只是少掉這條捷徑(`test_serving_from_a_side_thread_still_works_without_a_handler`)。
- **`SIGHUP` 也算「使用者說停」**(決策 12 只點名 Ctrl-C 與 `SIGTERM`):因為
  `--help` 與 README 都寫「關掉終端即失效」,而預設處置下關終端是**被殺**,在途的
  解密會留下明文片段——要讓那句話是真的,它就得走同一條乾淨退出。Windows 沒有這個
  信號,故 `_STOP_SIGNALS` 以 `getattr` 取。
- **順序**:先 `make_server`(綁 socket)→ 印那一行 → 開瀏覽器(**背景執行緒**)
  → `serve_forever` → 關 listen socket → 等在途工作 → 等瀏覽器執行緒。先綁才知道
  `--port 0` 配到哪個埠,也才能在埠被占時「什麼都還沒印」就乾淨失敗;而 socket 在
  `make_server` 裡就已經 listen,所以瀏覽器比 `serve_forever` 早到只會排在 backlog 裡。
- **退出預算攤開**:`UI_DRAIN_SECONDS=3.0`(在途的 `/api/*` 工作)+
  `UI_BROWSER_SECONDS=0.5`(開瀏覽器那條執行緒)= 最壞 ≈ 3.5 秒,留 1.5 秒給
  AC 第 3 條的 5 秒。常見情況(沒有在途工作、`--no-browser`)實測 0.01 秒。
- **`server_close()` 在 `finally` 且在 drain 之前**:`ui` 可能是一個跑很久的行程,
  不能靠行程結束來收 listen socket;先關它才等在途工作,等待才會收斂(不再有新
  連線進來)。

## 人側驗收項(worker 能力上限,ADR-002 決策 14)

`webbrowser.open` 真的開起一個瀏覽器、以及頁面在真瀏覽器裡的互動,worker 驗不到
(沙箱無瀏覽器)。本票驗到的是「`open` 被呼叫一次、參數等於印出的那一行」與
「那一行上的 port / token 真的能通 `/api/inspect`」;**合併前的人側驗收**建議:
`qvault ui` → 瀏覽器自動開啟 → 網址列的 `#token` 立刻被 `history.replaceState`
抹掉(#23)→ 三個表單各跑一次 → 終端 Ctrl-C → exit 0 且頁面後續請求全部失敗。
這一輪另外值得人側看一眼的兩點:**① 一邊解一個大檔一邊按 Ctrl-C**——終端應該停
住最多 3 秒把它做完(或印那行 `gave up after 3s …`),`out_dir` 裡不該留下
`.qvault-*.part`(worker 側已用 512 MiB / 2 GiB 兩個尺寸各量過一次,見 F1 那節的
表);**② 關掉終端視窗**(而不是 Ctrl-C)——行程應該一樣乾淨收掉。
