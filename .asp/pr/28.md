### L1-a `Content-Length`:為什麼 `int()` 不夠

本機 3.12.14 實測(測試裡有一條 `test_int_accepts_three_forms_the_rfc_does_not`
把這個前提釘住):`int("+12")` → 12、`int("1_000")` → 1000、`int(" 12 ")` → 12。
RFC 9110 §8.6 的文法是 `1*DIGIT`,所以這三形都不是合法的 `Content-Length`,而
修正前的 `int()` + `length < 0` 只擋得住 `-1` 與 `abc`。危害不是「多收一個請求」,
是**我們算出來的長度與線上那串位元組的宣告不再是同一回事**——下一個解析者對同一
個標頭算出不同長度,就是 request smuggling 的原料。

判形用 `frozenset("0123456789").issuperset(raw)` 而不是 `re.fullmatch`:
`tests/test_webui_server.py::test_webui_is_stdlib_only_besides_the_core` 把本檔的
import 集合**凍住**(裁判凍結,不得改),多一個 `import re` 當場紅。集合判定與
那條正則同義。

### L1-b `Transfer-Encoding`:擋整個標頭,不只擋 chunked

標準庫的 `BaseHTTPRequestHandler` 從頭到尾不支援 chunked 請求(只看
`Content-Length`),所以修正前一個 `Transfer-Encoding: chunked` 的請求在這個伺服器
眼裡是「body 長度 0」,而線上那串 chunk 還留在 socket 裡 → 被
`handle_one_request` 當成**下一個請求的請求行**。門 1.2 擋的是**整個標頭**(不管
有沒有同時給 `Content-Length`):同時給兩個是 RFC 9110 §6.1 明令要拒的那一種,
給一個我們不認識的編碼則連 body 都解不出來——讀不懂框的請求一律 fail-closed。

**順手關掉 `.asp/pr/25.md` 記的那條「已知殘留」**:#25 當時的結論是「chunked 打到
`/api/*` 會被當空 body → 400 → `_error` 的無條件 close 收場;打到**靜態路由**則仍
可能殘留」。門 1.2 在路由之前,所以 `GET /` + chunked 現在也是 `400` + close,殘留
的前提(連線還活著、還會解析下一個請求)不再成立。`_respond` 的那段 docstring 已
照實改寫。

### L2 的兩個附帶改動(**超出 AC 字面,但 AC 不這樣做就交不出來**)

裁定 2 選的是「覆寫 `error_message_format` / `error_content_type`」,而 AC 要的是
`GET / HTTP/9.9` 的回應「body 為 `{"error": ...}`、`Content-Type: application/json`、
三個安全標頭都在」。**只覆寫那兩個屬性交不出後兩項**,查證如下:

1. **`default_request_version = "HTTP/1.1"`**(新增一行類別屬性)。
   `parse_request` 是**先**把 `self.request_version` 設成 `default_request_version`
   (標準庫預設 `HTTP/0.9`)、**後**才去解版本欄的;而基底類別的 `send_header` /
   `end_headers` 整段包在 `if self.request_version != 'HTTP/0.9'` 裡。於是
   `GET / HTTP/9.9`(`505`)在送回應的那一刻 `request_version` 還是 `HTTP/0.9`:
   **狀態行與所有標頭一個都不發**,線上只有一份裸 body。改掉這個預設值之後,那條路
   才發得出 `Content-Type` 與決策 10 的三個標頭。代價是真正的 HTTP/0.9 請求
   (請求行只有兩個詞)也會收到一份 HTTP/1.1 的回應——1996 年就被取代的協定沒有
   客戶端還在送,而「這個伺服器永遠不發一份沒有 `Content-Type`、沒有 `nosniff` 的
   裸 body」是守得起的保證。`parse_request` 對兩個詞的請求行本來就設
   `close_connection = True`,所以也不會多出 keep-alive 的連線。
   (AC 的另兩筆——畸形請求行 `400`、請求行超長 `414`——在 `send_error` 之前就已經
   把 `request_version` 設成 `''`,本來就發得出標頭;`505` 是唯一踩到這個洞的。)

2. **`error_message_format` 裡刻意沒有 `%(message)s`**,body 是
   `{"error": "request rejected (HTTP %(code)d)"}`。基底類別給的 `message` 轉述
   請求行(`Bad request syntax ('…')`、`Invalid HTTP version (9.9)`),而請求行是
   攻擊者寫的:(a) 把它回顯進 body 與 `log_error` 整個收掉要防的是同一件事換個
   出口;(b) 基底類別對它做的是 `html.escape(message, quote=False)`——`"` **不會**被
   處理,所以一個帶引號或反斜線的請求行就能把這份 JSON 折斷,`json.loads` 當場
   失敗,決策 8 的「錯誤一律 JSON」會被一個畸形請求行打掉。`%(code)d` 是狀態碼
   本身,故這份 body 的每一個 byte 都是我們自己寫的,而且必定是合法 JSON
   (`test_the_error_format_is_valid_json_for_every_status_it_can_carry` 直接對格式
   斷言)。

3. **`send_response` 覆寫:reason phrase 一律用標準短語**。同一句理由的另一半:
   `send_error` 把那些訊息當 reason phrase 傳進 `send_response`,於是攻擊者的字串
   出現在我們說出口的**第一行**(`HTTP/1.1 505 Invalid HTTP version (9.9)`)。body
   那一側已經由第 2 點擋掉,狀態行是同一條路的另一半;而這一行只有在第 1 點之後
   才真的會被送出去,所以它是那個改動的**後果**,不是另一件事。
   順帶讓一個「有前提才成立」的保證變成無條件:`Invalid HTTP version (%s)` 用的是
   `%s` 而不是 `%r`,版本欄只需過 `str.isdigit()` 與 `int()`,而
   `send_response_only` 以 `latin-1`、`strict` 編狀態行——一個 `isdigit()` 為真卻編不
   成 latin-1 的數字(`'٩'`,U+0669)會讓回應在送的途中拋 `UnicodeEncodeError`,
   客戶端連一個狀態碼都收不到。**今天它打不進來**,理由與 `_escaped` 的表上緣同一
   個:請求行是 `iso-8859-1` 解出來的,U+0000–U+00FF 裡 `isdigit()` 為真的只有
   ASCII 十個數字與 `²³¹`,後三個 `int()` 不收(本世實測)。標準短語是純 ASCII 的
   模組常數,改用它之後這個保證不再依賴那個前提。

`_error` 的 docstring 照實修(裁定 2 的最後一句):「唯一出口」限定成「**本層自己
判出來的**錯誤的唯一出口」,並寫明第二個出口是基底類別的 `send_error`、兩者**同
形**的理由是上面那三個覆寫。`_respond` 的「本層唯一的回應出口」同樣加了限定詞。

## 跨票對帳:`414` 不在 #25 fuzz 的允許集合裡(裁定 4 的最後一句)

請求行 > 65,536 bytes 在標準庫走 `send_error(HTTPStatus.REQUEST_URI_TOO_LONG)` =
**414**,而 `tests/test_webui_fuzz.py::ALLOWED_STATUS` 是
`{200, 400, 401, 403, 404, 405, 409, 413, 415, 422}`——**沒有 414**。

**今天不衝突**:那份語料以 `http.client` 發請求,`PATH_CHARS` 隨機 path 最長 64 個
字元、`FIXED_PATHS` 更短,打不出 65,537 byte 的請求行。本票**不改** #25 的測試
(裁判凍結),只把事實釘在新檔的
`test_the_over_long_request_line_is_414` 裡:哪天有人把 fuzz 的 path 長度放寬,
他會在那條測試的 docstring 看到這個碼的存在與這段對帳。

同一段也記下 **`505`**:`GET / HTTP/9.9` 的狀態碼是 `505`(不是 `400`——
`parse_request` 對 `version_number >= (2, 0)` 走的是
`HTTP_VERSION_NOT_SUPPORTED`),它同樣不在那個集合裡,同樣因為 `http.client` 不
送壞版本而打不到。

## 已知殘留(本票不做,逐條說明)

1. **重複的 `Content-Length` 標頭**。`Content-Length: 5` 與 `Content-Length: 6` 同時
   出現時,`self.headers.get(...)` 取的是第一個,於是我們算 5 而別的解析者可能算
   6——與 L1-a 同一族的 smuggling 形。AC 沒有這一條(它列的是五個**值**的形),
   而本票的範圍條款寫「不自行擴張範圍」,故**不做**;`get_all("Content-Length")`
   長度 > 1 即 `400` 是三行的修法,留給下一張票。注意 `Content-Length: 5, 5`
   (單標頭、逗號分隔)**已經**被 L1-a 擋掉(逗號不在 `[0-9]`)。
2. **狀態行的 reason phrase 不再回顯請求行,但狀態碼本身仍是標準庫決定的**
   (`505` / `414` / `400`),本票沒有把它們收斂進決策 14 的封閉集合——那要改
   `handle_one_request` 或整個不走基底類別的 `send_error`,遠超 L2 的「回應形式」。
   見上面的跨票對帳。
3. **HTTP/0.9 不再被當成 0.9**(`default_request_version` 的代價,見上)。這是刻意
   的取捨而不是遺漏,理由寫在那一行的註解裡。
